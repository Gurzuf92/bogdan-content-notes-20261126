Почему я сохраняю исходный HTML перед отправкой статьи в CMS

26 ноября 2026 · Техническая заметка

Сохранённый HTML помогает понять, на каком этапе изменилась статья. До отправки есть версия редактора, после сохранения — представление в CMS, после публикации — страница читателя. Если сравнивать эти состояния отдельно, легче описать проблему и исправить существующую запись.

Я Богдан Коломиец, разрабатываю SEO Writer. В этой заметке разбираю небольшой приём из работы с веб-публикациями: сохранять исходный фрагмент и проверять смысловую структуру после переноса. Пример ниже учебный; он не содержит клиентских данных.

Что оставить рядом с исходником

Для короткого материала достаточно файла с HTML и небольшой карточки: заголовок, версия, дата подготовки и назначение текста. После сохранения в CMS к карточке добавляется идентификатор записи. Он помогает найти тот же материал при следующей проверке.

В исходник для разбора не нужны пароли, параметры входа или приватные адреса предпросмотра. Если проблему можно показать на двух абзацах и списке, я предпочитаю такой пример полной копии рабочей статьи. Его проще прочитать и передать другому разработчику.

Версию стоит обозначать до отправки. Иначе файл с названием «финал» легко превратить в несколько разных документов. Для небольшой проверки подойдут простые обозначения A, B и C, если рядом записано, что изменилось.

Почему одинаковый вид ещё не означает одинаковую структуру

Нумерованные абзацы могут выглядеть как инструкция, хотя в HTML они остаются отдельными параграфами. Для последовательности действий существует элемент ol: его назначение описано в справке MDN об упорядоченных списках. Внутри него каждый шаг оформляется как li.

Такое различие полезно проверять вместе с заголовками и таблицами. Размер шрифта сам по себе не делает строку заголовком, а пробелы между словами не заменяют строки и ячейки таблицы. Внешний вид и структура отвечают на разные вопросы.

Три состояния одного материала

Представление Что с ним сравнивать
Исходный HTML Принятую редакторскую версию текста и её структуру
Сохранённая запись CMS Переданный материал, идентификатор и параметры записи
Страница посетителя Текст, заголовки, ссылки, изображения и доступ без входа

У CMS могут быть собственные правила обработки содержимого. Поэтому различие между исходником и сохранённой версией сначала нужно описать, а затем выяснить его причину. Не каждое изменение пробелов или служебного атрибута означает потерю содержимого.

Маленький пример для воспроизведения

<h2>Проверка перед публикацией</h2>
<ol>
  <li>Открыть предпросмотр.</li>
  <li>Проверить порядок шагов.</li>
</ol>

Для такого фрагмента можно записать простой ожидаемый результат: один заголовок второго уровня и один список из двух пунктов. После вставки в редактор нужно проверить и вид, и итоговую разметку. Если список превратился в обычные абзацы, это уже конкретное наблюдение для разбора.

В этом примере нет запроса к рабочему сайту. Его удобно использовать как маленький образец текста, когда требуется проверить перенос разметки без публикации чужой статьи.

Что записать после сохранения в CMS

Я отдельно фиксирую, к какой записи относится результат операции. В описании WordPress REST API для записей идентификатор, ссылка, статус и содержимое представлены разными полями. Сохранённый ID полезен для продолжения работы с тем же материалом.

В рабочей карточке я оставляю следующие наблюдения:

  1. Какую версию текста передали.
  2. Какой идентификатор получила запись.
  3. Что видно в редакторе после повторного открытия.
  4. Что видно посетителю по опубликованному адресу.
  5. Какие отличия требуют исправления.

Если проверка не закончилась, её результат остаётся незавершённым. Повторное создание записи только из-за неясного уведомления может усложнить разбор: появится ещё один материал, который тоже придётся найти и сверить.

Где заканчивается такая проверка

Снимок HTML помогает сравнить версии. Он не устанавливает достоверность всех утверждений статьи, права на изображения или наличие страницы в поиске. Для этих вопросов нужны отдельные источники и наблюдения.

Для меня полезный итог — понятная запись о том, что именно проверено. Следующий человек получает исходник, версию и результат, с которого можно продолжить работу.
